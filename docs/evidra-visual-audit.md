# Evidra 核心工作台视觉审查与重设计方向

审查日期：2026-09-06  
审查对象：Evidra 面试演示 Preview 工作台  
基线地址：`https://geo-content-checker-aolqoe3a3.vercel.app/dashboard`

## 审查范围与证据

本轮覆盖以下核心链路：

- 首页 / Dashboard 空工作区
- 审查创建（项目 + 标题 + 正文）
- 分析中（排队 / 运行 / 取消）
- 问题诊断（读者问题、诊断结论）
- 修改建议（Patch、复制、加入修改清单）
- 报告总览（评分、摘要、复查入口）

真实浏览器证据：

- [桌面端空工作区基线](../output/visual-audit/baseline/desktop-empty.png)
- Chrome 无障碍树记录：页面标题为“Evidra · AI 内容可信度审查”，主标题为“AI 内容发布前审查工作台”，空态为“还没有项目 / 选择一个项目”。

限制：当前 Preview 的项目创建请求在浏览器中停留在“创建中”，未能取得服务端项目响应，因此无法把分析中、诊断、Patch 和完成报告状态制作成真实线上截图。本轮不伪造这些截图；这些页面的审查依据为真实代码路径、组件结构和状态文案，后续编码完成后会补齐状态截图。

## 总体结论

当前版本已经有完整的业务骨架，但仍然是“后台模板 + 表单”的表达方式。用户第一次打开时看见的是项目管理、额度和流程步骤，而不是 Evidra 真正的产品价值：把一篇内容拆成读者问题、证据链和可执行的修改动作，并支持修改后复查。

### 1. 首页 / Dashboard

**视觉层级问题**

- H1、三个指标卡、流程条、项目卡的字号与表面权重接近，首要动作不突出。
- “创建项目”是第一步，却被放在左侧窄卡中；右侧大面积空白反而成为视觉焦点。
- 面试模式、当前工作区、刷新等系统状态挤在顶部，抢占了主任务上下文。

**通用后台模板区域**

- 固定白色侧栏、细顶部栏、三张统计卡、双列内容卡是典型 CRUD 控制台结构。
- “我的项目 / 0 / 30 次审查 / 新建项目”像通用 SaaS 管理后台，而不是内容审查产品。

**产品记忆点缺失**

- 首屏没有内容片段、问题证据、风险色带或“发布前可信度”视觉锚点。
- Evidra 的差异化词汇“证据、风险、复查”只出现在说明文字，未成为界面对象。

**状态可见性问题**

- 空工作区只能看到“选择一个项目”，没有明显的“一键开始审查”路径。
- 0 项目、0 次审查和“待选择”同时出现，用户很难判断下一步是创建项目还是提交正文。

**密度与信息结构**

- 左侧内容拥挤，右侧留白过大；信息密度不随任务推进变化。
- 流程条是静态说明，不是可感知的当前状态容器。

### 2. 审查创建

**视觉层级问题**

- 项目创建、标题输入、正文输入、开始分析按钮都采用同一表单语气，没有“输入内容 → 检查范围 → 提交”的分段节奏。
- 正文编辑器缺少字数、内容类型、目标受众或检查范围等上下文提示。

**模板感与记忆点**

- 普通 label + input + textarea 的表单组合高度通用。
- 没有把正文视为“待审查证据对象”，也没有预览/摘录/检查点提示。

**状态问题**

- 重新分析、首次分析、额度不足、空内容等状态主要通过按钮文字变化，缺少独立状态区域。
- 错误提示在表单底部，未绑定到具体字段或动作。

### 3. 分析中

**视觉层级问题**

- 排队中、分析中、刷新状态、取消按钮都位于运行历史和表单附近，层级容易被淹没。
- 运行状态没有阶段进度，用户不知道当前在提取问题、检查证据还是生成 Patch。

**状态可见性问题**

- 只显示“排队中 / 正在分析”，缺少预计耗时、已完成步骤、失败原因和可恢复动作。
- 取消与刷新是并列按钮，容易让用户误判哪个是主动作。

### 4. 问题诊断

**视觉层级问题**

- 读者问题、诊断结论、问题数量在结果区中以折叠段落和摘要列表呈现，重要性差异不够。
- 诊断结论是长段落，缺少问题级别、证据来源和定位信息。

**产品记忆点缺失**

- “证据链”没有独立的可视化结构；问题没有连接到正文片段或事实依据。
- 风险没有统一的严重度颜色和可筛选维度。

### 5. 修改建议

**视觉层级问题**

- Patch 是一段 `pre` 文本，编辑方向和执行动作混在一起。
- “复制 Patch / 加入修改清单”虽已存在，但没有清单计数、完成状态和回到正文的连续流程。

**状态问题**

- 复制成功、加入清单、修改后复查通过等反馈只改变按钮文案，反馈存在时间短且缺少总览。
- 没有展示“已处理 / 待处理 / 跳过”的修改项状态。

### 6. 报告总览

**视觉层级问题**

- 总分、读者问题、诊断结论、Patch 建议均为同级白色模块，缺少“先看风险，再看证据，最后执行”的阅读顺序。
- 复查结果只在底部追加，无法形成前后对比的闭环。

**通用模板区域**

- 摘要卡 + details 折叠块 + pre 代码块是常见 AI Demo 结果页组合。

**产品记忆点缺失**

- 没有“风险 → 证据 → 修改 → 复查”的可视化主线。
- 报告更像模型输出容器，而不是内容发布前的决策工作台。

## 可访问性与可用性风险

- 当前部分状态主要靠颜色和小字，低视力用户难以区分当前、完成和错误。
- 空态操作入口不够集中，键盘用户需要在导航、指标、流程条、项目表单之间移动较多次。
- 折叠区的摘要文案不足以说明展开后内容的优先级。
- 移动端将多个区域纵向堆叠后，主动作和状态反馈可能被推到较深位置；需要在 390px 视口验证。

## 三个完整视觉方向

### 方向 A：Evidence Desk / 证据工作台（推荐）

**页面构图与信息层级**

- 页面从“管理项目”改为“处理一篇内容”：顶部是审查对象和当前阶段，中间为正文/问题/证据三栏工作面，右侧为风险与动作栏。
- 首屏只保留一个主动作：提交或继续审查；项目列表降级为可切换的工作区抽屉。
- 报告按“风险摘要 → 证据链 → 诊断问题 → 修改清单 → 复查变化”纵向推进。

**色彩、字体和设计语言**

- 暖白纸张底色 + 深墨色正文 + 靛青主色，风险使用橙/红，证据使用蓝绿。
- 标题使用高对比的 Geist/系统无衬线，正文采用更舒适的 14–15px 阅读字号。
- 设计语言偏编辑器、审稿台和标注工具，而不是商业后台。

**导航与内容区**

- 左侧窄轨只保留工作区、项目切换、报告；顶部显示审查对象、阶段和保存状态。
- 内容区采用“主文档 + 证据侧栏”，在报告页切换为“问题队列 + 证据详情 + 修改动作”。

**风险、证据链、诊断表达**

- 风险按严重度分成高/中/低三档，使用带文字的色带和数量。
- 每个诊断项都显示：问题、正文定位、证据缺口、建议动作；点击后在右侧展开证据链。

**状态**

- 加载：阶段型进度轨道（提取问题 → 核对证据 → 生成建议）。
- 完成：报告头部显示完成时间、评分变化和可执行下一步。
- 错误：就地显示失败阶段、恢复动作和是否会重复扣额度。
- 筛选：风险级别、问题类型、是否已处理；展开：保持队列上下文不跳页。

**桌面 / 移动**

- 桌面使用 2:1 主文档与证据栏；移动端变为“摘要 → 问题队列 → 证据抽屉”，正文和证据通过底部切换条切换。

### 方向 B：Risk Control Room / 风险指挥台

**页面构图与信息层级**

- 首屏以风险总览为核心：左侧风险分布，中间问题队列，右侧当前运行与发布门槛。
- 内容正文作为可展开的“证据源”，不直接占据首屏。

**色彩、字体和设计语言**

- 深石墨背景、荧光黄/红/青绿状态色，等宽数字和紧凑网格。
- 更像安全控制台和运营指挥中心，强调状态、阈值和变化。

**导航与内容区**

- 左侧为阶段导航，顶部是项目与运行状态，中央为可筛选问题表。
- 报告总览是一张“发布门槛卡”，明确通过/阻塞原因。

**风险、证据链、诊断表达**

- 以风险矩阵、严重度柱条和状态点表达；证据链在表格行内展开。

**状态**

- 加载采用实时事件流；完成显示“门槛通过”；错误显示系统事件和重试策略。

**桌面 / 移动**

- 桌面保留三栏指挥台；移动端优先风险摘要和阻塞问题，表格转换为卡片队列。

### 方向 C：Review Canvas / 审查时间线画布

**页面构图与信息层级**

- 以一次审查为中心，沿纵向时间线排列：提交 → 问题 → 证据 → Patch → 复查。
- 项目和历史记录成为时间线上的上下文筛选，而不是常驻左侧卡片。

**色彩、字体和设计语言**

- 低饱和灰白画布 + 蓝紫阶段节点 + 纸张卡片，设计语言偏研究笔记和协作画布。

**导航与内容区**

- 顶部是审查标题与阶段导航，主区是可展开时间线，右侧为当前节点详情。

**风险、证据链、诊断表达**

- 风险挂在时间线节点上；证据以“引用片段 → 依据 → 结论”的链条卡片展示。

**状态**

- 加载表现为时间线节点逐步点亮；完成显示闭环；错误节点保留在原位置并提供恢复。

**桌面 / 移动**

- 桌面使用时间线 + 详情侧栏；移动端改为单列节点流，详情以底部抽屉出现。

## 选定方向

本轮选定 **方向 A：Evidence Desk / 证据工作台**。

理由：它最适合面试演示，能在第一屏直接回答“Evidra 和普通 AI 文案工具有什么不同”；它把已有业务链路完整映射成可讲述的产品结构，同时不需要改动鉴权、支付、API 或数据库。方向 B 更偏成熟运营产品，方向 C 更适合复杂协作场景，均不如方向 A 适合当前单人面试作品。

## 编码边界

本轮允许重做：布局、组件层级、设计 Token、导航结构、卡片/列表、报告组织、动效和交互反馈。  
本轮禁止改动：鉴权、支付、API 合约、数据库模型、服务端额度扣除与运行状态语义。

编码顺序：

1. 先建立 Evidence Desk 的页面骨架和 Token；
2. 再重排 Dashboard、创建、运行、报告和复查状态；
3. 增加风险筛选、诊断展开、Patch 清单和状态反馈；
4. 完成桌面与 390px 响应式；
5. 运行 lint、typecheck、测试、build；
6. 重新采集桌面、移动和主要交互状态截图，并记录仍存在的问题。
